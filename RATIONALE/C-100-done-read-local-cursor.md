# C-100 完成提醒的已读/未读用「本地已读游标 + 多通道标识」承载，不复用宿主确认态

日期: 2026-10-16

#### 上下文
东家反馈（2026-10-16）：已完成的会话「已读/未读标识不明显」（窗格「已完成」分区与侧栏角标弹窗两处），并要求「会话标记为已读后『已完成』标签不再持续闪烁」。

约束事实：完成提醒的真值有两套已存在的状态——宿主持久化的**完成确认**（ackedAt，写回宿主、跨客户端同步、解除提醒并把卡片迁入历史区，R-01-002/AC-10、AC-11）与客户端本地的**已读游标**（`dsh-activity-pane:done-read`，会话「已读到此回合结束」的本地记忆）。二者语义不同：打开会话不是确认（R-01-002/AC-05 明确），确认也不是阅读。已读游标此前只有窗格「已完成」分区消费（实心/空心状态点 + 标题加粗），弹窗与侧栏角标完全不知道它。

另一条约束：末行脉冲是三类等待行动共用的提醒通道（R-01-002/AC-07、AC-08，C-043、C-065），阻塞等待与错误提醒没有已读语义，不能因为给完成提醒加门控而让它们的行为改变。

#### 决策
1. 已读判定收敛到 core 单点：`classifyActiveEntries(entries, doneReadById)` 在归类时就地写入完成提醒条目的 `unread`；窗格「已完成」分区、角标弹窗条目与角标未读读数共用该字段，不再各持一份判定。
2. 已读只改本地游标、不碰宿主确认账本：`markDoneRead(sessionId)` 把游标推进到条目当前 `stateAt` 并持久化；窗格卡片激活与弹窗条目激活**都**写这份游标——两条路径是同一次「我看过了」，否则同一会话在弹窗里读过、在窗格里还挂未读。
3. 标识做多通道，不只靠颜色：窗格卡片用「实心/空心状态点 + 左缘绿色色条 + 标题字重 + 整卡 0.72 弱化」四通道，文案通道由 `doneWaitLabel` 给出「已完成（未读）/已完成」；弹窗条目用「状态点实心/空心 + 标题字重 + 状态文字『未读/已读』」；侧栏角标用静态未读提示环 + 无障碍名称里的未读条数。颜色仅作辅助（色觉障碍用户拿不到纯颜色语义）。
4. 脉冲门控写在末行脉冲规则本身，且只门控完成提醒分支：`[data-wait="done"][data-unread]` 与「非 done」两支共用同一条 `dap-pulse 1.2s`；已读的完成提醒（属性被摘除）不落在任何脉冲规则内。**没有**为已读引入新的动画或缩短周期——它是「停止」而不是「换一种闪」。
5. 左缘色条用 `::before` 而非 `border-left`：等待卡面与当前会话卡以整边 `border-color` 着色、定义在本规则之后且特异性更高，边框着色会被顶掉（实测当前会话的未读完成卡左缘显蓝，e2e 断言抓到）。

#### 被否方案及原因
- 用宿主 ack 状态（ackedAt）充当已读：会把「打开会话」变成「解除完成提醒」，直接违背 R-01-002/AC-05 与 DOMAIN 的「打开会话不构成确认」，且已读是全客户端的确认动作、跨端同步语义过重。
- 已读后改播更弱的动画（如更慢的呼吸）而不是停：东家要求的是「不再闪烁」，且用弱动画承载已读等于给已读再分配一个注意力通道，与「已读=我看过了」的语义相反。
- 只在窗格「已完成」分区加标识、弹窗维持现状：两处呈现同一份数据却给出不同状态，用户在弹窗点到会话后窗格才变已读，属于同一状态的两个面互相矛盾。
- 用禁用按钮/置灰整卡承载已读：会把「已读完」与「不可用」混淆；0.72 弱化沿用了最近历史卡既有的淡化手法（R-01-013/AC-10），语义是「不重要」而非「不可用」。
- 未读提示环也做成闪烁：闪动通道已由「需要交互」占用（C-099），再给「已完成」加闪会让两个状态在侧栏争夺同一注意力通道；未读是「有东西等你看」，不是「必须立刻行动」。
