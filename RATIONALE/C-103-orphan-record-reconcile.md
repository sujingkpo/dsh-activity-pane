# C-103 会话离开会话服务列表即清理宿主侧孤儿记录，以启动对账兜底存量

日期: 2026-10-19

#### 上下文
东家 2026-10-19 反馈：「工作区删除对应的会话后，活动会话需要同步删除」。实测这台机器的提醒登记表与累计运行时长记账表各含 64 条记录，其中 3 条对应的会话已不在磁盘上；这些记录永不被任何代码删除，随删除次数无限增长。

同时查实一个关键事实：本机安装的 `dsh-sessions-manager` 的「删除会话」是软删除——只写 `~/.dsh/sessions-manager-trash/index.json`，既不动磁盘日志也不动宿主 `sessions.list`，它自己的侧栏靠读回收站索引来隐藏。经与东家两轮确认（东家先选「不判定已删」，在被指出矛盾后仍选「坚持只做从 sessions.list 消失，接受软删期间仍显示」），本决策不读回收站索引，只覆盖「会话真的从会话服务列表消失」这一场景（宿主移除、彻底删除、日志被清理后重连）。

约束事实：宿主侧提供了一份权威的会话全集读取入口，且持久化表的键删除能力存在——可以直接移除记录而不只是写空值。

#### 决策
1. 触发时机取两处：会话移除的实时信号（`session/disposed`，宿主 `api-session/removed` 的同源事件）与插件启动时的一次对账扫描。
2. 对账口径：`acks` 与 `turn_stats` 中每个 sessionId 若不在 `sessionQuery.listSessions()` 的返回集合内，即 `delete` 该记录；单条失败只记 warn，不阻断其余记录。
3. 实时路径只删该 sessionId 的记录，不做全量扫描；删除后照常 `broadcast()` / `broadcastBusy()`，客户端经既有 SSE 收敛。
4. 不读第三方插件的回收站索引、不调其 HTTP 接口：本插件「无第三方插件依赖、卸载可逆」的约束优先；软删除期间的残留按东家裁定接受，并在交付说明写清边界。
5. `turn_stats` 的重建无需专门处理：会话若重新出现（恢复/回滚），下一次 `/busy` 请求的懒回填会按日志重建记账。

#### 被否方案及原因
- 读 `~/.dsh/sessions-manager-trash/index.json` 当「已删集合」：能覆盖软删场景，但把本插件的正确性绑到另一个插件的私有文件格式上，且格式变化时只能静默降级；东家在明确指出这层取舍后仍选择不引入耦合。
- 调会话管理器 `/archived-sessions/sidebar-state`：格式有公开承诺，但引入运行时第三方依赖，与 README「无第三方插件依赖」的既有承诺冲突。
- 只在启动时对账：运行期间删除的记录要等下次重启才消失，两个 storages 文件在长会话期间持续膨胀。
- 顺手在客户端做过期记录裁剪：客户端不掌握权威会话全集，只能按「本帧不可见」裁剪，会把暂时不可见（紧凑档、折叠、超出历史分页）的正常会话记录误删。
