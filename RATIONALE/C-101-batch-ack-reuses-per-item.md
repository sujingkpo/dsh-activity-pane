# C-101 批量「全部移入历史」复用逐条完成确认写回，而非新增批量端点

日期: 2026-10-16

#### 上下文
东家在同一轮反馈中追加（m00407）：「右侧侧边栏的 再增加全部移入历史」——即窗格「已完成」分区段头与角标弹窗「已完成」组段头各加一枚批量入口。此前只有逐张卡片的「移入历史」按钮（每卡一条 POST /dsh-activity-pane/api/ack，乐观更新 + 失败回滚，见 C-030），段头上只有刚加的「全部已读」（纯本地游标动作，R-01-026/AC-13）。

约束事实：完成确认是宿主侧持久化状态，写回路径已有单一实现 ackCompletion(sessionId)；批量入口若自建通道或自建状态，会产生第二套解除语义与第二套失败处理。另外，用户一次处理掉整批时，把它们留在未读态没有意义。

#### 决策
1. 批量动作 = 逐条复用：ackAllDone() 取当前 doneEntriesById 的 id 集合，逐个调 ackCompletion(id)；每条各自乐观更新与失败回滚，一条失败不影响其余。
2. 先已读再确认：批量提交前先 markAllDoneRead()——同一次用户动作里没有理由留下未读残留。
3. 两处入口同一动作、两种外观：段头各一枚 .dap-done-all，窗格与弹窗调用同一个 ackAllDone()；外观取中性次要按钮（绿色留给无副作用的「全部已读」），以「是否写回宿主」区分语义重量。
4. 显隐按分区条数（与未读无关）：分区里没有完成提醒时整枚隐藏，可访问名称给出条数。

#### 被否方案及原因
- 新增批量 ack 端点（如 POST /api/ack-all）：宿主侧要多实现一套批量语义与部分失败处理，而逐条写回本身已经是幂等、可逐条回滚的；为省几次请求引入第二种解除路径不划算。
- 复用「全部已读」按钮承载批量确认（如长按或二次点击）：把「只看不解除」与「解除提醒」两个语义压进同一控件，误触代价是提醒被清掉，风险不对称。
- 批量入口也做成绿色胶囊（与「全部已读」同款）：两者外观一致会让人以为都是无副作用动作，而这一枚会真正把卡片迁出分区——按后果分色，不按位置统一。
- 加二次确认对话框：完成提醒是可逆的（会话再有新回合即重新提醒），且该动作本就是在用户点开「移入历史」的同一位置，加重流程反而拖慢清场。
