# C-098 角标与弹窗的数据通路抽离窗格渲染面（派生前置 + 独立去重键）

日期: 2026-10-14

#### 上下文
东家反馈（2026-10-14）：宿主侧栏「活动会话」入口行的三状态角标与点开的弹窗，依赖右侧栏「活动会话」停靠页签处于打开状态；角标应在会话被关闭后仍在后台持续运行，不依赖前台打开。停靠模式下属实：该页签是唯一停靠 tab，用户关闭即整列收起，插件正文组件卸载并使右栏宿主引用归 null，渲染函数在窗格不可得时整轮早退——角标刷新位于其后，计数与明细冻结在关栏那一刻（回归用例在未修复代码上以超时复现）。窗格渲染签名去重是第二处早退，同样位于角标刷新之前。角标的数据来源（会话列表、工作区、运行状态、完成确认）本就与窗格 DOM 无关，耦合只是执行顺序造成的。

#### 决策
把「活动模型派生」抽为窗格无关的独立函数并前置于渲染函数入口，渲染函数在取得窗格之前先派生、再按窗格可得性分流；角标刷新收口为单一入口，在窗格缺席、骨架未就位与在屏三条路径上各调用一次，且三处均位于窗格渲染签名去重之前；角标另起一路去重键（计数三元组 + 三组明细 id），不与窗格渲染签名共用；三类计数取活动状态模型的单点口径函数，渲染层不再就地重算副本；角标与弹窗的刷新不再依赖窗格脉冲面参数。

#### 被否方案及原因
- 保留既有单入口，只在窗格不可得时另跑一段「角标专用派生」：同口径逻辑出现两份，后续任一侧调整都会漂移，且两份派生各自记账订阅与回收，成本翻倍。
- 让角标直接订阅宿主会话服务并自行重算：与窗格卡片的口径（主会话三类归属、完成提醒读状态、档位过滤）会分叉，且重复建立会话列表/运行状态订阅，违背「订阅数量与运行中会话数量一致」类纪律。
- 窗格缺席时用既有的有界重试重新打开右栏页签：与此前已确立的「用户手动关闭 tab 是明确意图、插件不得再推回面板」相冲突，且把「后台持续运行」实现成「前台被强行打开」。
- 仅把角标刷新提到渲染函数第一行、仍沿用窗格句柄：窗格不可得时派生数据拿不到，等于回到原症状。
