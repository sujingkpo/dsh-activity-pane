# C-102 错误提醒卡开放显式确认解除，与完成提醒共用同一枚 ack 写回（修订 C-043「错误卡不提供按钮」的子决定）

日期: 2026-10-19

#### 上下文
东家 2026-10-19 反馈：「错误的会话可以移入历史，或标记已完成」——即错误提醒卡也需要一条用户可主动清场的路径。C-043 当时裁定的相反结论（「错误卡提供『移入历史』按钮」被列入被否方案）建立在两个前提上：其一，错误提醒随新回合结束覆盖解除即可，不必额外动作；其二，错误卡需要「会话仍可对话」这一警示语义，加了确认按钮会让用户误以为错误已被处理。

实测推翻了第一个前提：错误回合结束后若用户不再向该会话发消息（常见于批量跑任务、某会话因 429 重试耗尽而停下），`lastTurnEndKind` 会永久停留在 `error`，该卡就永久停在活动区且永不消失——用户没有任何手段把它清出视线，只能重启宿主或等它自己再来一回合。这与「活动区应反映当前要处理的会话」直接冲突。第二个前提随之松动：错误提醒与完成提醒在「用户已看到并决定不再处理」这一点上语义相同，用户主动确认即表达「我知道了」。

约束事实：既有写回通路只有一条 `POST /dsh-activity-pane/api/ack` → `acks.put(sessionId, {..., ackedAt: Date.now()})`，`ackedAt` 已是「用户确认时刻」的持久游标；完成提醒的成立判定正是 `lastTurnEnd > ackedAt`。

#### 决策
1. 错误提醒卡提供与完成提醒卡同一枚「移入历史」按钮（不叫「标记已完成」，两类卡共用同一文案与同一 `.dap-confirm` 节点）。
2. 写回路径不新增：点击仍是 `ackCompletion(sessionId)` → 同一 `POST /api/ack`，只推进 `ackedAt`。
3. `errorReminder` 改为消费 ack 游标：`lastTurnEndKind === 'error'` 且（`ackedAt` 不可得或 `lastTurnEnd > ackedAt`）即成立；确认后该错误提醒解除，条目落回最近历史区。
4. 错误提醒与完成提醒的互斥优先级不变（同一 `lastTurnEndKind` 只能命中一类）；新回合结束仍覆盖解除，确认是第二解除路径而非替代。
5. 卡片视觉与文案不变：红色卡面、红色「错误」胶囊、错误信息正文；按钮沿用次要按钮外观与「不参与脉冲」纪律。

#### 被否方案及原因
- 维持 C-043 的「错误卡不提供按钮」：实测存在永久无法清场的错误卡，用户只能重启宿主——这是本次反馈的直接动因。
- 错误卡按钮文案改叫「标记已完成」：错误回合并未完成任何工作，文案会说谎；且会引入第二套按钮文案与第二个可访问名称分支，而两者的物理后果完全相同（都只推进 ackedAt）。
- 给错误提醒单独开一条 `POST /api/dismiss-error` 端点：同一物理后果的第二条通路，多一套失败处理与多一处状态来源，违背单一解除语义。
- 错误确认同时清掉 `lastTurnEndKind`：会让「该回合以错误结束」这一持久事实消失，刷新后无从判断，也破坏「随新回合覆盖解除」的既有判定；只推进 `ackedAt` 可保留事实。
